OfferClaw 网页端上线改造分析报告

生成日期：2026-08-26 项目版本：v1.2.0 分析范围：全项目代码 + 架构文档

一、项目现状概述

OfferClaw 是一个 Agent 驱动的求职管理平台，当前架构为 FastAPI 后端 + 原生 JS 前端 + Chrome 扩展。项目目前以 PyInstaller 单文件桌面端形式分发，所有功能围绕单用户本地运行设计：

  • 鉴权层为 open 模式，所有请求固定为 local-user，无真实用户体系
  • 数据库使用 SQLite 单文件，存储在 backend/data/offerclaw.db
  • Playwright 以本地子进程方式运行，用于 Boss 搜索和智能填表
  • 授权采用机器绑定 JWT（MAC 指纹 + 离线验签）
  • 限流器为内存滑动窗口，仅支持单进程
  • 前端无构建系统，由 python -m http.server 或 FastAPI StaticFiles 托管

二、需要改造的 8 大模块

1. P0 用户体系与鉴权（最核心）

现状问题：auth.py 硬编码 LOCAL_USER_ID = "local-user"，所有请求视为同一用户。数据模型中 user_id 字段虽已预留（String(64), index=True），但无 User 表、无注册/登录/密码/会话管理。

需要做的工作：

  • 新建 User 模型（id/email/password_hash/created_at/last_login/subscription_tier）
  • 实现注册/登录 API（密码哈希用 bcrypt/argon2，JWT 签发 + refresh token）
  • 可选接入 OAuth 第三方登录（微信扫码 / GitHub / Google）
  • 重写 get_current_user()：从 Authorization: Bearer 解析 JWT 获取真实 user_id
  • 所有 API 路由的 Depends(get_current_user) 改为注入真实用户 ID
  • 前端增加登录/注册页面，token 存 httpOnly cookie（非 localStorage，防 XSS）
  • CSRF 防护（SameSite cookie + CSRF token）

2. P0 数据库迁移（SQLite → PostgreSQL）

现状问题：SQLite 单文件不支持并发写入，database.py 虽已预留 DATABASE_URL 环境变量切换，但多个模块有 SQLite 特定写法（JSON 类型用 sqlalchemy.dialects.sqlite.JSON，check_same_thread 参数）。

需要做的工作：

  • Profile 模型改用 sqlalchemy.JSON（通用类型，兼容 PG 的 JSONB）
  • 移除 connect_args={"check_same_thread": False}（PG 不需要）
  • 引入 Alembic 做 schema 版本管理（当前是 auto_migrate 手动列追加，不适合多实例）
  • 连接池配置（pool_size、max_overflow、pool_pre_ping）
  • 数据迁移脚本：将现有 SQLite 数据导入 PostgreSQL

3. P0 容器化与部署

现状问题：README 明确标注 Docker 部署 ❌ 未提供。当前用 PyInstaller 打包为 exe，单机桌面运行。

需要做的工作：

  • 编写 Dockerfile（Python 3.11 slim + Playwright 系统依赖 + Chromium）
  • 编写 docker-compose.yml（app + postgres + redis 三容器编排）
  • Nginx 反向代理配置（TLS 终结、静态文件服务、API 转发、SSE 代理）
  • 前端构建为静态资源（Vite/esbuild），输出到 dist/，由 Nginx 或 FastAPI StaticFiles 托管
  • 环境变量管理（secrets 不入镜像，通过 docker secrets / k8s secrets 注入）
  • CI/CD 流水线（GitHub Actions / GitLab CI：lint → test → build → push → deploy）

4. P1 Playwright 服务化

现状问题：Playwright 以本地子进程方式运行，每个请求同步等待浏览器操作完成。在网页端高并发场景下，单进程无法支撑多用户同时使用 Boss 搜索 / 智能填表功能。

需要做的工作：

  • 将 Playwright 操作抽离为独立微服务或任务队列（Celery / RQ / Dramatiq）
  • 浏览器池管理（预启动多个 Chromium 实例，复用 context，隔离用户数据）
  • 异步任务模式：前端提交任务 → 返回 task_id → 轮询/WebSocket 获取结果
  • 超时与资源回收（单个任务最长执行时间、空闲浏览器自动关闭）
  • Boss 登录态管理：从本地浏览器 profile 改为服务端 session 池 + 用户扫码绑定
  • 反爬风险：服务端 IP 被封后需要代理池策略

替代方案：将 Boss 搜索降级为纯 HTML 公开页解析（已有 boss_html_search.py），智能填表功能改为 Chrome 扩展端执行（已有扩展能力），Playwright 在服务端可选/受限使用。

5. P1 授权模型重构（机器绑定 → SaaS 订阅）

现状问题：license.py 的机器绑定模式（MAC 指纹 + 离线 JWT 验签）不适合网页端。网页端用户不绑定机器，需要的是账户级订阅/配额管理。

需要做的工作：

  • 新建 Subscription 模型（user_id/plan/started_at/expires_at/usage_quota/used_count）
  • 订阅层级：免费版（限制功能/配额）/ 基础版 / 专业版
  • 用量计费：LLM 调用次数、Playwright 任务次数、Agent 对话轮数
  • 移除或重构 license_gate_middleware：从机器授权 → 用户订阅校验
  • 支付接入（微信支付 / 支付宝）
  • 复用已有 subscription.py 框架（当前为 Mock，需实现真实逻辑）

6. P2 前端改造

现状问题：前端为原生 HTML/CSS/JS，无构建系统、无组件化、无类型检查。api.js 中 API 基址依赖 location.hostname 判断环境，config.js 中 TOKEN 硬编码为 internal-beta。

需要做的工作：

  • 引入前端框架（推荐 Vue 3 + Vite，迁移成本低；或 React + Vite）
  • 将现有 7 个视图（chat/kanban/jobs/profile/smart-fill/interview/settings）迁移为组件
  • 路由系统（Vue Router / React Router），替代当前手写 hash router
  • 状态管理（Pinia / Zustand），管理用户登录态、主题偏好等
  • 构建产物部署到 CDN，API 请求走相对路径（Nginx 反代到后端）
  • 移除前端硬编码 TOKEN，改用 httpOnly cookie 自动携带

轻量方案：保持原生 JS，仅加 Vite 做构建 + 代码分割 + 环境变量注入，不做框架迁移。适合快速上线 MVP。

7. P2 安全加固

现状问题：当前为内测模式，CORS 配置宽松，无 HTTPS，无安全头，SSE 无鉴权。

需要做的工作：

  • HTTPS 全站强制（HSTS header）
  • CORS 精确配置（只允许正式域名，移除 localhost 和通配符）
  • 安全头：CSP / X-Frame-Options / X-Content-Type-Options / Referrer-Policy
  • SSE 端点鉴权（当前 Agent 对话 SSE 无 session 校验）
  • 输入验证与 XSS 防护（已有 esc() 函数，需确保所有动态内容使用）
  • SQL 注入防护（SQLAlchemy ORM 已参数化，需审计 raw query）
  • 速率限制改用 Redis 后端（当前内存版不支持多实例）
  • 密钥管理：LLM API Key 不再由用户在前端配置，改由服务端统一管理

8. P2 隐私合规与敏感数据处理

现状问题：敏感信息（身份证/住址/银行卡）仅存浏览器端，后端 sanitizer.py 强制剔除。网页端若用户换设备/清缓存，敏感数据丢失。

需要做的工作：

  • 端到端加密方案：服务端存储加密后的敏感数据（用户密码派生密钥，服务端不可解密）
  • 用户隐私协议与数据处理说明
  • GDPR/个人信息保护法合规：数据导出、删除、匿名化
  • Chrome 扩展适配：扩展从连本地后端改为连线上后端，API 基址可配置

四、建议的上线策略

阶段一：MVP 快速验证（4-6 周）

  • Docker 化 + PG + Redis 基础设施
  • 用户注册/登录（仅邮箱密码）
  • 前端仅加 Vite 构建，不迁框架
  • 砍掉 Playwright 功能（Boss 搜索降级为 HTML 解析，智能填表保留扩展端）
  • 部署到云服务器，邀请内测用户

阶段二：完整功能（4-8 周）

  • Playwright 服务化（任务队列 + 浏览器池）
  • SaaS 订阅 + 支付
  • 前端迁移到 Vue/React
  • 安全加固 + 隐私合规
  • CI/CD + 监控

阶段三：运营优化（持续）

  • 移动端适配 / PWA
  • 性能优化（CDN、缓存、DB 索引调优）
  • 用户反馈驱动迭代
